# Use non-listable protected media resources

Identify ready Stored Media no larger than 16 MiB (`16,777,216` bytes) with `whatsapp-media://connections/{connection_id}/messages/{message_id}/media/{media_id}` for MCP and the authenticated nested path `/v1/connections/{connection_id}/messages/{message_id}/media/{media_id}` for REST, and return those concrete links from authorized message reads. Ready requires a non-null verified plaintext byte size and normalized MIME type; unknown MIME normalizes to `application/octet-stream`, inability to verify size makes processing `failed`, and filename may remain null. The verified byte size is an integrity-protected queryable operational field so eligibility, audit, and full-size quota reservation occur before content or encrypted metadata is decrypted. Ready media above that separate readable limit remains retained with its metadata but has no MCP resource URI or REST path; MCP message reads report `too_large_for_mcp` and the limit, while REST message reads report `too_large`. This avoids base64 expansion against the Workers 128 MiB memory ceiling without lowering ingestion limits, adding chunk semantics, or issuing bearer URLs in the MVP. Advertise only the MCP URI template and keep `resources/list` empty, avoiding a bulk media inventory. Every resource read strictly parses the URI or nested path, rechecks the current MCP Authorization or API Key and full ownership chain, durably audits and reserves bytes before decryption, and returns private non-cacheable binary content; unknown, unauthorized, mismatched, non-ready, and over-limit handles share one not-found boundary. Do not emit directly fetchable HTTPS, provider, public R2, or presigned URLs because they bypass or inconsistently carry authorization.
