# Platform-manage Wasender sessions

The platform waitlist clause below is superseded by ADR 0026; Clerk is now the sole waitlist authority and provider-capacity exhaustion is transient service unavailability.

The platform owns the Wasender accounts and credentials used to provision one provider session per WhatsApp Connection, so a User does not need a Wasender account or API key. Account-level PATs exist only in a private provider-control Worker and are restricted to provisioning and lifecycle operations; normal connection operations use the narrower session-specific credential. Provider-control also owns the Webshare API credential used to assign one unused, static Colombian ISP SOCKS5 proxy to each provider session through Webshare's public Backbone hostname. One named Durable Object represents the environment's single proxy pool and serializes create, reconcile, repair, and reconnect validation. Before a proxy-changing write it durably reserves the pool with only the opaque Connection Setup marker and a settlement deadline; definitive completion releases the reservation, while an ambiguous write retains it until safe reconciliation observes the outcome. It never stores a proxy assignment or credential because Wasender remains the provider-configuration observation. Proxy inventory must remain Colombian and automatic refresh stays disabled; creation fails closed when no valid unused proxy is available, while reconciliation repairs missing configuration without rotating an existing valid assignment. Provider message logging and automatic incoming-message reads are always disabled because the encrypted Message Store is the authoritative history and passive ingestion must not alter WhatsApp read receipts. Until vendor-approved enterprise capacity exists, onboarding stops at the documented session ceiling and uses a waitlist rather than unapproved account sharding or bring-your-own credentials. Production launch is contingent on written Wasender terms for enterprise session capacity, data processing and subprocessors, data deletion, security controls, webhook authentication and retries, because the public plans and documentation do not currently provide adequate guarantees for a scaled multi-tenant service.
