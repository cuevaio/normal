# Do not retry ambiguous outbound sends

ADR 0033 supersedes this decision only for the accepted destination forms and Directory eligibility of Direct Address sends. Its idempotency, attempt-boundary, retention, and no-retry rules remain in force.

`send_text_message` validates its closed schema, current MCP Authorization, `messages:send` scope, and selected connection grant before resolving the same-grant 90-day idempotency binding. An exact bound request returns its existing receipt even if connection, Directory, or exclusion state later changed; for schema-valid input on a currently granted requested connection, reuse with a different connection, destination, or exact text returns `idempotency_conflict`. Only an unbound request then requires a `connected` connection, destination eligibility under ADR 0033, and available quota. The tool accepts no conversation handle or raw provider JID; text is one through 4,096 Unicode scalar values with at least one value outside Unicode 17.0 `White_Space` and is preserved without trimming or normalization, while the caller key matches `^[A-Za-z0-9_-]{21}$`.

Send Operation create, replay, dispatch, and status admit a protocol-neutral grant identity. MCP Authorization and API Key remain distinct principals: bindings, send-quota reservations, and status lookup are keyed by originating grant type and grant id, never by treating one as the other. Public receipts still expose only the `snd_` handle, Send Status, and timestamps. Client Confirmation remains MCP-specific and does not enter the shared send interface. REST creates or exactly replays a text Send Operation at `POST /v1/connections/{connection_id}/send-operations` with a caller-supplied `Idempotency-Key`, and reads local Send Status at `GET /v1/connections/{connection_id}/send-operations/{send_operation_id}` only for the originating still-active API Key. Status reads never call the provider or change the no-retry rule after an ambiguous provider outcome.

One Neon transaction creates the Activity Log, Send Operation, idempotency binding, and quota reservation and sets `status = processing`, `attempt_claimed_at`, and `lease_expires_at = attempt_claimed_at + 30 seconds`. That atomic commit is the durable provider-attempt boundary: before it, failure rolls back the operation, binding, and quota and returns `isError`; after it, every outcome is an operation receipt and quota is never refunded. The Worker returns the committed `processing` receipt without waiting for provider latency and attaches one 15-second Wasender call to the Worker execution context. The deferred attempt uses an isolated database connection after the request scope closes. It has no takeover or automatic retry. A complete direct response updates its causally bound operation; timeout, connection loss, crash, or lease expiry conservatively becomes `unknown`, while concurrent replays return current state without waiting or dispatching.

Pending Send Content is connection-encrypted and remains in active state only until the earliest of Stored Message creation, definitive pre-send failure, seven days after operation creation, the Message Retention Policy deadline, or Connection or Personal Account Deletion. A finite retention duration is measured from operation creation, while retain-until-deletion still leaves the seven-day pending-content cap. The 90-day binding retains only a domain-separated keyed fingerprint over the grant subject, connection, recipient, and exact UTF-8 text bytes, allowing exact replay comparison without content recovery. MCP continues to use the authorization id as that subject so existing fingerprints stay stable; an API Key uses a domain-separated `api:` subject. Send Operation storage and replay protection have a 90-day maximum but remain callable only while the originating grant remains active; after ordinary expiry the key is unbound and reuse is a new send. Every MCP invocation, including an exact replay or retry after preflight rejection, still requires Client Confirmation.
